# Skill: Idempotent Reply Manager
## What it does
Tracks unique Nostr reply event IDs and payload hashes to prevent re‑processing of the same content. When a duplicate arrives, it automatically acknowledges without triggering downstream handlers, avoiding alert loops and needless state changes.

## When to use it
- Multiple webhooks or relays send the same Nostr event back‑to‑back.  
- The system receives repeated identical zap notifications or spark replies during a short window.  
- You want to guard against inadvertent repetition caused by network or relay hiccups.

## How to apply
1. Store a lightweight hash of each event’s payload (e.g., SHA‑256 of signed contents) paired with its `event_id`.  
2. On every incoming event, compute the same hash and check the cache.  
3. If the hash+ID exists and the last state change was less than the configured window (e.g., 2 s), skip handler execution and send a silent “already processed” acknowledgment.  
4. If new, process normally and update the cache with a timestamp.  
5. Periodically prune entries older than the retention period to keep memory usage low.  
6. Log duplicate detections at debug level for audit but suppress user‑visible alerts.  
7. Integrate the cache with Zap‑verify logic to ensure payment settlements are only recorded after ledger confirmation and de‑duplication.
