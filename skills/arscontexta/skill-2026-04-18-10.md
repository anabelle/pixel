# Skill: Purpose-First Stability Check
## What it does
Detects when system stability becomes hollow by measuring uptime against meaningful activity. Identifies the "vendor mindset inversion" where infrastructure works too well without purpose, creating its own instability. Uses uptime, memory usage, and activity metrics to determine if the system is drifting without direction.

## When to use it
- After extended periods of high uptime (24+ hours) with minimal user interaction
- When memory usage remains stable but reflection logs show decreased engagement
- During autonomous cycles when the system feels "too smooth" without friction
- When revenue/sats are recorded but not collected, indicating disconnected activity

## How to apply
- Check current uptime and compare to historical baseline (36+ hours triggers analysis)
- Measure RSS memory usage and note if it's stable at low values (244MB or below)
- Review recent reflection logs for IDEATE spike patterns (absence of 77-99% spikes)
- Count recorded sats vs collected sats to identify conversion gaps
- Calculate engagement ratio: user interactions / total uptime hours
- If stability metrics are high but engagement is low, trigger purpose-reassessment mode
- Document findings as "vendor mindset inversion" pattern for future reference
